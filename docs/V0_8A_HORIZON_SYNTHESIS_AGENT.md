## Role and execution boundary

`src/horizon_synthesis.py` implements `synthesize_horizon(context)` under
`horizon-synthesis-v2`. It immediately invokes `require_synthesis_ready` and uses
the recomputed context. Rejected, blocked or forged contexts cause zero OpenAI calls;
readiness errors retain their reasons. No research is refreshed or regenerated.

Deterministic Python owns admission, freshness, applicability, authority, conflict,
policy versions and matrix constraints. The agent interprets only admitted evidence.
The same existing OpenAI client/model uses Responses, strict JSON schema,
`require_completed=True`, output_text extraction, JSON decoding and local validation.
There is one request, no retry, fallback, specialist rerun or persistence.

## Result and provenance

The frozen IntegratedResearchView composes the complete validated context with an
immutable JSON interpretation, application UTC completion timestamp, model identity
and synthesis methodology. Its accessor returns a detached dictionary. Source
conclusions, native horizons, confidence, conditions, evidence, provenance and limits
remain unchanged in the context. They are not regenerated by the model.

Software inserts ticker, decision horizon, authority, conflict and both conclusions;
public equality checks remain as defense in depth. Trusted metadata is retained by
composition rather than entrusted to AI. The prompt includes the source catalog rows and interpretations,
not raw historical bars or Fundamental portfolio_assessment. Source namespaces stay
separate. No portfolio position, weight, cost, cash or concentration is consumed.

## Research-only posture and confidence

Approved postures are FAVORABLE_NOW, WAIT_FOR_CONFIRMATION, UNFAVORABLE_NOW,
NO_ACTION and UNRESOLVED. Matrix rows define permitted ranges, never select output.
As explicitly allowed in Step 4, UNRESOLVED is available for residual interpretive
ambiguity in a ready context; it cannot bypass blocked input. NO_ACTION is an informed
lack of a compelling stance, not a failure fallback. WAIT must cite a supplied
condition in its summary.

Confidence is an independently assigned integer 0–100 measuring evidence strength
for the combined interpretation. It is not profit probability, expected return,
accuracy or an arithmetic transformation of specialist scores. No weights or
confidence arithmetic are implemented.

## Evidence, conditions and limits

Each statement has separate Fundamental/Technical evidence IDs, classification and
condition references. Every citation must exist; unavailable Technical evidence
cannot support a claim. Summary grounding requires both namespaces. Supporting and
conflicting lists remain separate. Source invalidation/confirmation lists are
preserved unchanged. Deterministic packet-local condition IDs reference those lists;
the model cannot introduce a new condition ID. Invalidation summaries must reference
original invalidations and their cited evidence.

AI_INTERPRETATION and FORECAST are the only generated statement categories.
Condition-bearing statements are FORECAST. Common explicit predictive language is
rejected outside FORECAST. Numeric facts stay in the catalogs: generated prose may
use exact cited indicator labels but no other digits. Explicit portfolio actions,
orders, stop levels and price-target language are rejected. This deliberately
conservative rule follows the existing Technical Analyst style.

Software inserts all deterministic warning/missing-data tokens exactly and in
order; the complete original limitations remain in the returned context regardless.
The output cannot erase them or change blockers into warnings.

## Failure handling

HorizonSynthesisError uses safe classifications: API_REQUEST, RESPONSE_EXTRACTION,
INVALID_JSON, SCHEMA_VALIDATION, INVALID_ENUM, INVALID_EVIDENCE_REFERENCE,
IDENTITY_MISMATCH, SEMANTIC_VALIDATION, DRAFT_VALIDATION or ASSEMBLY. Safe substages
separate request, extraction, decoding, draft validation, assembly and public validation.
Logs contain fixed stage/operation/type only,
never raw response text, prompts or keys. Readiness failures remain
SynthesisReadinessError. Malformed JSON and code fences are rejected, not repaired.

## Step 6L — Condition references and FORECAST

The exact `_validate.statement` predicate is `if c and
value['classification'] != 'FORECAST'`, where `c` is the validated set from
`condition_ids`. It emits HORIZON_SYNTHESIS_CONDITION_REQUIRES_FORECAST.
References must be exact packet condition keys, not evidence IDs or lexical mentions.
`_packet` enumerates Fundamental thesis invalidations as `F_INVALIDATION:<index>`,
Technical invalidations as `T_INVALIDATION:<index>` and Technical confirmations as
`T_CONFIRMATION:<index>`. There are no separate Fundamental catalyst/risk condition
namespaces. All narratives and integrated risk statements use the same rule.

Any valid nonempty condition reference requires FORECAST, regardless of wording,
tense, horizon, authority or posture. Confirmation and invalidation are equal for
this check. Independently, invalidation_summary must cite invalidations, and WAIT
requires a source condition in synthesis_summary. Condition evidence references
must also be included. Merely mentioning a condition in text does not trigger this
structural predicate. A separate lexical rule checks selected predictive words.

Original source statements/categories remain unchanged in the returned context:
source preservation does not require rewriting or reclassifying them. Generated
condition-bearing interpretation is always categorized FORECAST under the existing
contract, even descriptive attribution. This label does not assert that an event
will happen. An AI_INTERPRETATION can describe source research without condition IDs,
but must not omit required references to evade invalidation or WAIT requirements.

RETRIEVED_FACT and CALCULATED_METRIC belong to source evidence and are not allowed
generated statement classifications. AI_INTERPRETATION describes current research;
FORECAST is required for condition references and forward-looking interpretation.
The schema permits both categories but does not encode their cross-field dependency;
post-response validation supplies that constraint. This is not a schema contradiction.

The prior prompt said forward-looking statements require FORECAST but did not make
its structural extension to descriptive condition attribution explicit. Relationship:
AMBIGUOUS, with existing documentation and validator consistent. Step 6L adds only
that prompt clarification, names the existing condition prefixes, and explains
separate source preservation. No schema, validator, category or methodology changed.

| Offline text category | Condition ID | Expected classification / actual result |
| --- | --- | --- |
| Analyst identified confirmation; source invalidation remains trend deterioration; source has a confirmation condition | Present | FORECAST required; AI_INTERPRETATION rejected with CONDITION_REQUIRES_FORECAST; FORECAST accepted |
| If momentum continues; confirmation requires positive momentum; thesis would weaken; watch for condition | Present | Same structural requirement and result |
| Condition may occur / has already occurred | Present | Same structural result; acceptance does not prove the claim is grounded or true |
| Current momentum / Technical signal / source contains a condition | Absent | AI_INTERPRETATION accepted; original source conditions remain preserved |
| Thesis would weaken if momentum turns negative | Absent | AI_INTERPRETATION rejected by the separate PREDICTIVE_TEXT_REQUIRES_FORECAST rule |
| If momentum continues; condition may occur; condition already occurred | Absent | Parser accepts AI_INTERPRETATION: known lexical/entailment limitation, not endorsement of future statements as current facts |

The matrix runs all available condition IDs and all actual statement fields. No
implementation defect against the approved structural contract was proven. Descriptive
attribution with a condition ID is intentionally not an AI_INTERPRETATION exception.
Unreferenced prose cannot be fully checked for tense or source truth by these rules.
No historical Step 6K wording was retrieved or reconstructed.

## Step 6N — Evidence-role scope and namespace diagnostics

`_validate` first validates all four top-level role lists against their own catalogs.
It then checks intersection of supporting/conflicting Fundamental IDs and, separately,
Technical IDs. Any nonempty intersection raises SEMANTIC_VALIDATION /
HORIZON_SYNTHESIS_EVIDENCE_ROLE_OVERLAP. The approved implemented scope is global
role-list exclusivity **within each namespace**, not exclusivity across all citations.
This follows the existing top-level contract and Step 6H inventory; it adds no new
statement-scoped role system. Authority and conflict classification do not affect it.

Supporting lists identify evidence for the combined interpretation; conflicting lists
retain evidence that qualifies or cuts against it. A source item cannot occupy both
global roles in its namespace. Individual narratives have untyped citation arrays,
not supporting/conflicting fields. The same ID can ground multiple narratives, including
narrower claims about evidence assigned to the global conflicting list. The system
does not model an ID as supporting one statement and conflicting with another via
structured per-statement roles; adding those fields fails schema validation.

Fundamental support with Technical conflict is valid. Equal suffixes or even identical
literal IDs in independently supplied catalogs are distinct by namespace. The parser
compares exact strings without trimming, case folding, prefix removal or canonicalization.
Cross-catalog literal equality is tested only at parser level, not by inventing a new
admissible source artifact. Duplicate IDs within a role and unknown/unavailable IDs
fail INVALID_EVIDENCE_REFERENCE before overlap checking; nothing is silently deduplicated.
Ordering does not affect intersection, but original list order remains preserved.
Condition IDs and preserved source-role lists are not included in this intersection.
Source divergence is explained with grounded narratives/conflicting references, not by
automatically duplicating global roles. No new conflict methodology is introduced.

Prompt relationship before clarification: AMBIGUOUS about exclusivity scope. Schema
arrays do not express set disjointness; the existing semantic validator does. Step 6N
clarifies top-level per-namespace disjointness and ordinary statement citation reuse.
No schema or validator predicate changed; no valid-response rejection defect proven.

Overlap errors now carry optional `evidence_namespace`, allowlisted to FUNDAMENTAL or
TECHNICAL and propagated through HorizonPipelineError. Other errors have null namespace.
No IDs, evidence text, model response or prompt is retained in this field. If both
namespaces overlap, existing first-failure ordering reports FUNDAMENTAL first. Historical
Step 6M namespace/IDs cannot be reconstructed from the old generic reason.

| Offline fixture | Expected and actual result |
| --- | --- |
| F or T supporting only; F or T conflicting only, with citations retained | Accepted |
| F supporting E001 / conflicting E001 | Overlap; FUNDAMENTAL namespace retained through combined boundary |
| T supporting known T ID / conflicting same ID | Overlap; TECHNICAL namespace retained through combined boundary |
| F E001 and T T001; multiple valid distinct refs | Accepted by existing rich fixtures |
| Identical literal ID in independent parser catalogs, F support / T conflict | Accepted; namespaces not collapsed |
| Same ID cited by multiple statements, including globally conflicting evidence | Accepted |
| Statement-level role fields | SCHEMA_VALIDATION; these roles do not exist in statement contract |
| Unknown ID or repeated ID within one role | INVALID_EVIDENCE_REFERENCE, before overlap; namespace diagnostic null |

All observed outcomes match the existing scope; no false positive or false negative

## Step 6V-D — Inactive Horizon v2 internal contract

`src/horizon_draft.py` defines the frozen internal draft and strict bounded schema.
`validate_horizon_draft(data, context)` recomputes readiness and builds the authoritative
packet before validating selections; a caller-supplied/model packet is not the public
entry point. No request, rendering or IntegratedResearchView construction is included.
**horizon-synthesis-v1 remains ACTIVE; horizon-synthesis-v2 is NOT ACTIVE.**

TEXT parts contain `kind,value`. FEATURE/CITATION parts contain
`kind,namespace,evidence_id`. Namespaces are explicit FUNDAMENTAL/TECHNICAL, not
inferred from evidence ID prefixes. FEATURE is Technical-only: current canonical
catalog labels are renderable; Fundamental uses CITATION. Repeated explicit selections
normalize in first-occurrence order without discarding parts. Raw Technical labels
in TEXT (including TEXT joined across zero-width CITATION parts) reject without repair.

Each statement is exactly one of two strict shapes: `parts,condition_ids` with a
nonempty unique known condition selection, or `parts,classification` with model-selected
AI_INTERPRETATION/FORECAST. Condition-bound drafts carry no model classification;
future assembly MUST assign FORECAST. Other predictive prose remains subject to public
validation in 6V-E; it must not be silently relabeled. Condition source dependencies
are checked for availability, not inserted into prose or assembled output here.

Role assignments contain namespace, evidence_id and SUPPORTING/CONFLICTING. One role
per namespaced ID; duplicate or opposite assignments reject. Empty roles remain valid;
there is no role/narrative equality requirement. Summary requires explicit selections
from both namespaces. Conditions alone are not statement evidence. Existing WAIT
requires a selected source confirmation OR invalidation in synthesis_summary, not
necessarily a confirmation specifically. This preserves the actual v1 rule.

source-available-invalidation-v1 remains: invalidation_summary selects an invalidation
when available, otherwise uses an unconditioned statement; confirmation never substitutes.
The packet retains NO_SOURCE_INVALIDATION_CONDITION when appropriate. Exact identity,
source conclusions, ordered limitations, policies and provenance are excluded from the
generated draft and remain upstream-owned for later assembly. Software insertion of
limitations will not prove model understanding.

Bounds: 128 parts per statement, 128 roles/conditions/risks, 8192 characters per text/ID.
Local validation enforces structural bounds, selections, posture/confidence, roles,
conditions and namespace grounding. Numeric/action/predictive prose checks remain at
the future rendered public boundary. Draft validity proves neither entailment nor
interpretation quality; dataclass construction is not a trust certificate. No active
Technical/Horizon schema, prompt, validator, admission or pipeline changes occurred.
